# Design taste

- Prefers a minimal, simple, clean UI aesthetic; dislikes gradient-heavy, neon, and decorative "showy" treatments and wants those specific things (gradients, colors) removed when flagged. Confidence: 0.8
- Prefers Inter as the UI typeface when given the choice. Confidence: 0.85
- Rejects generic, templated-looking output as "AI slop" and rejects designs that "look AI generated"; explicitly asks for results that feel subtle and aesthetically good, and expects a deliberately designed, high-end result. Confidence: 0.85
- When he dislikes a design, expects a full rebuild from scratch driven by the reference he names, not incremental restyling of the existing shell — the layout information architecture should change too, not just colors and fonts. Confidence: 0.7
- Communicates design feedback with reference screenshots and expects the implementation to match that reference's layout (including adding the screens/states it shows, e.g., a dedicated URL-entry page before the workspace). Confidence: 0.65
- Keeps iterating on visual direction and is comfortable with (and expects) wholesale redesigns across rounds rather than preserving earlier styling decisions. Confidence: 0.6
- Prefers modal/loading overlays to blur the underlying content and background (backdrop blur) so the active state is the sole point of focus. Confidence: 0.5
- Expects fluid, smooth animated transitions on interactive UI controls (e.g., a sliding-pill segmented toggle, an FAQ accordion's open/close) — motion quality is an explicit, stated requirement ("make sure to add smooth opening and closing effect"), not an afterthought, and he asks for it proactively on new interactive elements. Confidence: 0.65
- Prefers informational content sections (e.g. an FAQ block) to be genuinely interactive — collapsible/disclosure controls (accordion of buttons with expand-collapse) rather than a static list of terms and definitions. Confidence: 0.5
- Prefers UI content consolidated into coarse, readable units over exposing raw granular data row-by-row (e.g., merging ~2s caption fragments into ~30s+ transcript paragraphs) — the presentation should look clean and "precise". Confidence: 0.5
- Dislikes excessive whitespace in interfaces and prefers a tighter, denser composition that remains clean, aesthetic, and easy to scan. Confidence: 0.85
- When asking for a redesign, states the outcome standard ("shouldn't feel AI generated", "subtle, aesthetically good") and expects the agent to propose concrete visual directions to choose from before a full rebuild, rather than silently committing to one direction. Confidence: 0.5
- Wants UI copy and visual vocabulary to stay plain and literal — every label should say what the thing actually does. Explicitly rejects invented metaphors/themed jargon (e.g. dressing a summarizer as a TV control room with "File it", "Stories", "TRT", "on air", "Cutting the show"). Confidence: 0.8
- Expects the design scoped to what the product actually supports today: for a small single-purpose tool, no invented concepts, no borrowed industry language, and no visual framing that implies capabilities (billing, tiers, workflows) the app doesn't have. Calls scope inflation "overcomplicating things". Confidence: 0.8
- When scope creep or over-designed framing is flagged, expects it undone rather than defended — delete the offending metaphor/concepts and rebuild the affected screens to the real feature set. Confidence: 0.65
- Prefers media never start on its own: a summarized video should show a static thumbnail/poster and only play when the user explicitly asks, with no autoplay after an action completes. Confidence: 0.65
- Wants brand/logo marks to be genuinely legible and visible: flags a logo that renders "too short and not visible" and expects assets trimmed to their actual ink (so CSS size matches the type) and contrast fixed against the page background rather than left to fade into it. Confidence: 0.6
- When he supplies a design mockup/reference image, expects the implementation to match it "exact" — geometry, spacing, element scale and visual weight taken from the reference rather than approximated — while still harmonizing with the surrounding existing UI. He restates the bar as "it should be identical" and rejects a result that merely approximates the reference as still "looking weird", so a near-miss counts as a failure to be re-matched. Confidence: 0.85
- Judges mockup fidelity at the reference's own viewport/resolution: the comparison standard is the screenshot's own frame (e.g. 1672×941), so container width, column split, gaps and the whole internal scale of nested elements should be derived from the reference's proportions (its content column is ~91% of the viewport, not a guessed fixed width) rather than eyeballed against a different window size. Confidence: 0.7
- Expects a mockup reproduced in full, component by component — every distinct element in the reference (headline, field/input, cards, margin notes, corner labels, etc.) built out, not a subset or an overall "vibe" approximation; frames this explicitly as "match each and every component". Confidence: 0.55
- Supplies a whole set of reference images for a redesign — one per output mode/variant plus one per sub-feature state (e.g. four summary styles, the ask/notes/quiz panels) — and expects every one rendered as its own distinct layout, not collapsed into a single shared style. Confidence: 0.6
- Flags element scale explicitly when it looks off relative to the reference (e.g. logo and logo text "looking bigger") and expects the whole element's sizing to be corrected to the reference's proportions, not nudged slightly. Confidence: 0.6
- Prioritizes the app's own monochrome ink design system over literal reference/vendor defaults: when a mockup showed Clerk's default violet avatar, he chose to keep it ink-themed — design-system consistency wins over matching a third-party element's stock color exactly. Confidence: 0.55
- Keeps pages minimal and stripped of decorative/marketing-style chrome: asks for feature/benefit bullet lists (e.g. "YouTube captions / OpenRouter free models / No API keys or billing") and tagline corner labels (e.g. "Small videos / Big ideas", "Powered by AI / Built for learners") to be deleted rather than reworded — and re-asserts that same removal on each new screen he redesigns and on each pass over the landing page itself (repeated for the history page, the video page, and again for the landing hero's "From Videos to Knowledge" margin note), and expects the decorative arrows that sit with such taglines removed along with them — even when the note/arrow appears in the reference mockup he asked to match. Confidence: 0.75
- Expects card-like UI elements to have visible hover feedback — a lift, soft shadow, background/mark settling, and a subtle icon/nested-element response — so they acknowledge interaction, applying the effect to the whole group of sibling cards consistently. Confidence: 0.5
- Keeps design reference assets (mockups, background art) in the repo under `frontend/src/design/` and points the agent at them by path when requesting a visual change; expects the result to actually use that asset and still match the app's existing style ("make sure it matches the style"). Confidence: 0.6
- Willing to make a supplied illustration the site-wide background/ground layer (replacing the flat paper ground) when he asks for it, provided text surfaces stay legible on top and the treatment reads as part of the design. He enforces that legibility condition: when a closing section's copy has to sit over the busy illustrated ground and reads badly, he flags the section as "looking kind of weird" and asks for it to get its own clean, solid background band (e.g. the footer on plain white/card) rather than letting text land on the artwork. Confidence: 0.6
- Sources individual UI controls from third-party component galleries by URL (e.g. Rare UI's delete button) and expects the referenced component's interaction adopted but rewritten to fit the project's own stack and design system — no new dependencies and no vendor styling shipped as-is — as he puts it, "make sure to match with UI". Confidence: 0.6
- Expects a new UI control to be scaled and styled to blend with the app's existing controls and overall vibe, not left at the third-party component's default size — a control bigger than its siblings (44px when every other control is 34px) is called out as "big" and "not matching the whole vibe of the website", and he expects it resized down to the established control scale (the whole element, plus its panel/circles/radii/icons) so it reads as belonging to the product. Confidence: 0.6
- Expects user-facing error copy to name the real cause and the concrete remedy (which limit was actually hit, when it resets) instead of a vague generic like "The model is rate-limited right now. Try again in a moment." — he surfaces that kind of unhelpful message as the bug to fix. Confidence: 0.5
- Insists user-facing messages never expose internal infrastructure — no provider/model names, no "free model"/"free tier" wording, no quota/API-key/billing details, no raw request counts — because it makes the product look unprofessional ("it shows user everything like we are using free model"). The user should get a polished, plain-language message (state the situation + a calm next step like "try again later"); the diagnostic detail (source, limit, reset seconds) belongs in server logs. Confidence: 0.8
- When the redesign covers a whole page, supplies the reference both as per-section slices (e.g. landing-p1/p2/p3) and as one full-page composite (landing-full.png), names the composite as the finished standard ("make sure the final design should look like landing-full.png"), and leaves the implementation breakdown up to the agent ("in 3 part or whatever way you are comfortable"). Confidence: 0.55
- Explicitly requires any new/edited section to fit the app's overall aesthetic ("make sure to match the aesthetic of whole design") — harmony with the existing design language matters more than a reference mockup's literal details, and he will reject a section that is faithful to the reference but feels foreign to the rest of the page. Confidence: 0.6
- Prefers a content band placed over an illustrated/artwork ground to get a white background softened with a subtle backdrop blur (frosted white, e.g. `rgba(255,255,255,~0.78)` + `backdrop-filter: blur(...)`) so the art softens behind it — rather than the busy ground showing through crisply behind the text or being hidden under a flat opaque surface; he suggests the blur himself as an option ("if you can you can add a white background blur"). Confidence: 0.55
- Prefers prominent content bands — such as a closing CTA strip — to be held narrower than the page's full container width and centred, so the copy and its action button read as a single unit; at full width the elements drift apart and the empty middle reads as a dead gap he calls out ("make it little narrow ... it should not feel weird"), supplying a reference example of the narrower treatment. Confidence: 0.5
- Willing to introduce a second type family as a display face for large hero/headline type while the rest of the product stays in Inter — he asked for the landing "Watch Less. / Learn More." headline switched to Sora ("i want to change the font for part 1 ... i have attached the reference image of how it should look like"), superseding the earlier one-family rule. He specifies the face by pointing at a font specimen rather than naming sizes/weights. Confidence: 0.5
- Judges the page at the browser's default 100% zoom and expects the composition to hold there — a layout that only looks right when the browser is zoomed out is reported as a defect and expected to be fixed. Relatedly, expects the design to scale as one composition as the available width shrinks (type, spacing and drawn/nested elements shrinking together so their proportions stay constant), rather than only the outer columns narrowing while their contents stay full-size and crowd. Confidence: 0.55
