# General taste
- Prefers free, keyless, or no-billing solutions for AI/transcription dependencies where possible (YouTube captions via keyword-free services, free LLM tiers) over paid API keys. Confidence: 0.7
- Prefers solutions that add zero new npm dependencies (reusing already-installed SDKs pointed at alternative endpoints) over introducing new packages. Confidence: 0.7
- Values provider abstraction in AI-service code generally (env-driven model selection), BUT when committed to a single free provider (e.g., OpenRouter), prefers a lean, provider-specific implementation (plain `fetch` to that endpoint) over keeping a multi-provider switch that adds surface area. Confidence: 0.6
- Prefers keeping code in language/runtime style consistent with the project (CommonJS to match the project). Confidence: 0.6
- Wants styling done with Tailwind CSS utility classes exclusively — no custom class selectors in `style.css` (e.g. `.workspace`, `.header`); utilities go directly in `className` (e.g. `className="flex min-h-screen bg-white..."`). Expects this applied to the entire frontend, not just the screen he names last — he follows up a landing-page conversion by demanding "the entire frontend converted to Tailwind CSS, not just the landing page" (every screen: workspace, video pane, panels, quiz, history, home, header, menus, overlays, auth). Only CSS that genuinely cannot be expressed as utilities should remain. Confidence: 0.8
- Expects a styling/implementation refactor to be purely mechanical: the existing design and functionality must stay exactly the same, and copy that is now unused (e.g. orphaned CSS) must be removed rather than left behind. Confidence: 0.6
- Prefers configuration to be env-driven rather than hardcoded (e.g., allowed CORS origins and server PORT read from environment with sensible defaults). Confidence: 0.55
- Keeps secrets out of client-side bundles — no secret keys in frontend env or `VITE_`-prefixed variables (only publishable/public keys belong there). Confidence: 0.55
- Wants to become self-sufficient: after the agent performs setup/infrastructure work, expects a written, plain-language, step-by-step guide (exact commands) for doing it themselves in future. Confidence: 0.6
- When the agent makes a tooling/approach choice, wants the rationale explained plainly, including why it beats the obvious alternative the user names (e.g., Docker Compose vs. a native MongoDB/Compass install). Confidence: 0.55
- Prefers a modular file structure organized by concern — components in a `components/` folder, types in a dedicated types module, hooks/constants in their own files — rather than a single large component file. Confidence: 0.8
- Wants entry/container files kept as small and simple as possible, with every function that can live elsewhere extracted into its own module. Confidence: 0.75
- When specifying a visual/theme change, expects it applied consistently across the whole app (every page and state), not just the screen being edited — stated explicitly for a site-wide background ("make sure to make the bg for whole website"). Confidence: 0.6
- Gives tightly scoped UI-change requests and expects them applied only to the specified location — when a shared component renders in multiple places, only the named instance should change and the others must keep their current behavior. He states the boundary explicitly ("only for this specific video page", "don't change the main page or history page") and expects already-finished screens left untouched and un-regressed while a new one is redesigned. Confidence: 0.6
- Prefers the frontend isolated in its own top-level folder (e.g., `frontend/`) with its tooling and config (package.json, lockfile, tsconfig, vite/eslint config, .env.example) living inside it, leaving the backend and repo-level files untouched. Confidence: 0.7
- Expects the product's single brand name to be used consistently and correctly across every user-facing surface — third-party configuration (e.g., the Clerk application name) and metadata such as the browser tab title included, not just in-app code. Confidence: 0.55
- Treats responsiveness as a first-class requirement: when an operation feels slow he explicitly demands it be optimized ("taking too much time", "check if we can reduce that") and expects the agent to investigate and cut latency rather than accept it. Confidence: 0.75
- Prefers AI-generated output constrained to explicit, per-mode length budgets — a distinct word/line cap for each output style (concise vs. detailed) so results stay predictable and scannable instead of rambling. Confidence: 0.6
- Expects per-item state to be fully isolated: opening or switching to a different item (e.g. another video from history) must clear the previous item's derived state (answer, notes, quiz, in-flight loading) rather than carry it over. Confidence: 0.6
- Expects UI navigation to be reflected in the URL — distinct, deep-linkable routes for each screen/entity (e.g. `/history`, `/video/:videoId`) with working browser back/forward and refresh, rather than views driven purely by component state; he treats the absence of URL routing as a defect, asks why it isn't there, and explicitly asks for "proper routing" to be added once it's pointed out. Confidence: 0.65
- Expects an action that produces a new entity to route the user straight to that entity's page automatically, with no manual detour: once a video is summarized the app should land directly on that video's page, and he reports it as a bug when it instead errors or leaves him elsewhere and he has to reach the result via the list (history) page. Confidence: 0.55
