# Workflow preferences

- When choosing between technical options/providers, wants the agent to research and give a reasoned recommendation for the project's specifics before committing, and is receptive to that researched choice. Confidence: 0.7
- Prefers clean, complete removal of deprecated systems during a migration (e.g., removing the old auth stack, dependencies, dead middleware, and models entirely) rather than keeping temporary/parallel implementations or sync-stub bridges. Confidence: 0.7
- After completing a major implementation phase, wants a comprehensive summary of the app's full supported functionality/API surface, explicitly framed in terms of what downstream consumers (e.g., what the frontend needs to implement) require. Confidence: 0.6
- Before acting on new code dropped into the project, wants the agent to first inspect/read it and report findings (issues, mismatches) rather than immediately editing; discussion of fixes comes after the inspection. Confidence: 0.6
- After an inspection report of found issues, expects the agent to fix all of them — including minor cleanup/perf/config items — rather than asking which subset to address or fixing only the critical ones. Confidence: 0.55
- Does not want the agent to kill or disturb the user's own running processes (e.g., a dev server already listening on a port); prefers they be left alone and the change worked around (e.g., making the port configurable and verifying on a separate port). Confidence: 0.6
- Wants changes verified before being reported done: typecheck/build for the frontend, syntax check for backend files, and a live runtime test of the changed behavior (e.g., actually exercising the CORS change). For a broad refactor he enumerates the full gate set himself — "lint, typecheck, build, and browser checks" across the whole app — so all four should be run and reported. Confidence: 0.6
- Expects verification to go through the real, authenticated end-to-end path (e.g., minting a real auth session token and hitting the actual HTTP endpoints with it) rather than only testing the internal service layer, with throwaway credentials/artifacts cleaned up afterwards. Confidence: 0.5
- Wants infrastructure (e.g., Docker containers/databases) declared declaratively inside the repo — a tracked compose file, env example, and README setup note — rather than created imperatively outside the project where the recipe to recreate it isn't captured in version control. Confidence: 0.6
- Prefers large features delivered as an explicit, ordered plan he approves, then executed one approved phase at a time — waiting for an explicit "let's do phase N" / approval before starting the next phase rather than running the whole roadmap through. Confidence: 0.6
- Dislikes elaborate process ceremony around small tasks and will push back when the agent scales it up — both multi-round option-picking questionnaires, prototyping several alternative treatments, and heavy verification/analysis rigor. For a simple, clearly-specified change (e.g. restyling one button, swapping in a background image) he expects the agent to just make the edit, do one check, and stop rather than measure/diff/analyze repeatedly ("just to make a simple button change why are you taking soo much time?", "I over-did it again"). The same pushback applies to verification detours on larger tasks: when the agent spent a long stretch spinning up a browser preview, screenshotting pages and evaluating computed styles unasked, he interjected mid-task with "what is the issue? why taking soo much time?", so keep self-driven verification short and report progress rather than going silent through an extended check. Confidence: 0.75
- For design work, is comfortable with an interactive live-preview loop: pointing at the specific element in the running app and picking/steering among proposed variants in the browser (Impeccable live mode) rather than describing the change in text up front. Confidence: 0.55
- When an auxiliary tooling workflow stalls or fails to produce anything, prefers to cut losses and have it ripped out entirely ("f it let it be. remove the live for impeccable") rather than have the agent keep retrying/debugging it — and expects every artifact it injected into source (wrappers, HTML injection, markers) reverted cleanly and verified gone. Confidence: 0.5
- Prioritizes getting core functionality correct over visual polish — will explicitly defer design work ("we'll do it after we sort out the main functionalities") and expects functional bugs and performance fixed first. Confidence: 0.7
- When redesigning UI, prefers to go incrementally — "one component at a time" — rather than one wholesale rewrite, so each component can be settled before moving to the next. Confidence: 0.7
- When a design ships as numbered sections (e.g. landing-p1/p2/p3), sends and iterates one part at a time: "lets do it in parts", expecting the agent to rebuild only the named part to match its reference and leave the remaining sections at their prior state until their reference arrives — a finished-looking whole-page build can still be rejected and re-done section by section. He drives the sequence himself, advancing to the next part's reference only once the current one is settled (asks for part 3 after part 1, leaving part 2 on its earlier pass). Confidence: 0.75
- Brings in external agent skills as the evaluator — installing them from public repos himself (e.g. `npx skills add https://github.com/anthropics/skills --skill frontend-design`) — and expects the review turned into action in the same pass: judge the surface, then implement the improvements it identifies rather than stopping at the report. Confidence: 0.55
- When handing back work that an earlier session had started, pastes the original prompt as the spec and expects the agent to first establish what is already implemented versus what remains against it, then finish the entire remaining scope in one pass — and close with a final summary of the work ("check how much of this is made and what is remaining", "do the whole thing and give me final summery"). Confidence: 0.6
- Chooses work by felt, current-user impact: approves fixes he'll actually notice (progress/elapsed-time feedback on a slow wait, retry-with-backoff to smooth a failure) and explicitly declines optimizations/refactors whose only benefit is in scenarios his current usage never hits (e.g. was told "skip #3" for parallelizing a map-reduce loop that only matters for >100k-char transcripts — none of his qualify). Confidence: 0.5
- Sets explicit time budgets on sizeable tasks ("make sure do this task under 80 minutes") and expects the work delivered inside them — a stated deadline is part of the spec, so keep verification and self-directed detours within that budget. Confidence: 0.5
- Opens a fresh session mid-project by checking whether the agent still has context ("do you have a context about what we were currently building about redesigning?") and expects it to reconstruct the in-flight work from the repo itself — design docs, git status/log, plan files — and report where things stand, rather than asking him to re-brief it. Confidence: 0.5
- For reference-matching work he explicitly trades time for fidelity — "take as much time as you want but make it identical" — so unlike simple UI edits (where he pushes back on over-verification), pixel-exact mockup reproduction is the case where rigorous, measurement-driven matching is warranted before declaring it done. Confidence: 0.7
- When a later iteration looks worse to him, prefers reverting to the earlier version he'd accepted ("revert to how you first made") and reworking from that baseline rather than having the agent keep patching the current state forward. Confidence: 0.55
